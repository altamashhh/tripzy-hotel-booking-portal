# DESIGN.md -- Tripzy Hotel Booking Portal

## 1. Overview

Tripzy is a full-stack hotel booking portal built for the Thomas Cook
Full Stack Fresher interview assignment. It supports hotel discovery,
destination and date-based search, property details, room selection,
booking creation, booking retrieval, and cancellation.

The surprise feature is a rule-based Smart Stay Recommendation Engine
that filters and ranks room options using travel preferences.

## 2. Architecture

``` text
User
 |
 v
React + Vite frontend
 (pages, components, API service)
 |
 | HTTP / JSON
 v
Spring Boot REST controllers
 |
 v
Service layer
 (validation, availability, pricing,
  booking lifecycle, recommendations)
 |
 v
Spring Data JPA repositories
 |
 v
MySQL database
```

### Frontend

React renders the homepage, hotel details, booking form, booking
management, and recommendation experience. It collects search and guest
details, displays backend data, shows an estimated total, sends REST
requests, and displays success or error feedback.

The frontend estimate is informational. The backend calculates the
authoritative booking amount using the stored room price and number of
nights.

### Backend

Spring Boot controllers expose REST endpoints. Controllers delegate
business operations to services. Services apply validation and
booking/recommendation rules and use repositories for persistence.

-   Controllers: HTTP routing, request parameters, and response
    handling.
-   Services: validation, pricing, availability, booking lifecycle, and
    recommendation logic.
-   Repositories: persistence access through Spring Data JPA.
-   Entities: persistent hotel, room category, and booking data.

### Database

MySQL stores hotel, room category, and booking records. Spring Data JPA
maps Java entities to relational tables.

## 3. Database design

The main domain types are `Hotel`, `RoomType`, `Booking`, and
`BookingStatus`.

### Hotel

Represents a property. It contains property information such as name,
location, description, amenities, active status, and related metadata.

### RoomType

Represents a bookable room category belonging to a hotel. It includes
category, description, nightly price, guest capacity, total inventory,
and active status.

Relationship: one hotel can have multiple room types; each room type
belongs to one hotel.

### Booking

Represents a guest reservation. It stores guest name and email, unique
booking reference, hotel, room type, check-in and check-out dates,
number of rooms, total amount, status, and timestamps.

Each booking refers to one hotel and one room type. A hotel and room
type can be associated with multiple bookings over time.

### BookingStatus

Distinguishes confirmed and cancelled reservations. Only confirmed
bookings count against room inventory. Cancelled bookings are excluded
from availability calculations.

### Constraints and assumptions

-   Booking references are generated by the backend and are intended to
    be unique.
-   The current booking flow reserves one room per booking.
-   Check-in cannot be in the past.
-   Check-out must be strictly after check-in.
-   Number of nights is the date difference between check-out and
    check-in. The check-out date is not an occupied night.
-   Date ranges overlap when existing check-in is before requested
    check-out and existing check-out is after requested check-in.
-   Inventory is evaluated night by night. The maximum concurrent
    occupancy during the requested stay is compared with total room
    inventory.
-   The sample dataset contains 15 hotels across Mumbai, Goa, Jaipur,
    Bengaluru, and Manali.

## 5. Booking logic

### 5.1 Date validation

The backend requires both dates, rejects a check-in date earlier than
the current date, and requires check-out to be later than check-in.
Frontend validation provides immediate feedback, but backend validation
is authoritative.

### 5.2 Pricing

``` text
numberOfNights = checkOutDate - checkInDate
totalAmount = roomPricePerNight × numberOfNights
```

The frontend displays an estimate. The backend calculates and persists
the final amount using the room's database price; it does not trust a
client-supplied total.

### 5.3 Availability and overlapping stays

Two stays overlap when:

``` text
existingCheckIn < requestedCheckOut
AND
existingCheckOut > requestedCheckIn
```

Check-out is exclusive. For example, a guest checking out on 17 November
does not occupy the room on the night of 17 November, so another guest
can check in on that date.

The booking service retrieves confirmed overlapping bookings for the
selected room type and calculates occupancy for each night. It finds the
maximum number of rooms occupied on any night of the requested stay. A
new one-room booking is accepted only when:

``` text
maximumOccupiedRooms + 1 <= totalRooms
```

Cancelled bookings are not counted as confirmed bookings and therefore
release inventory.

The hotel availability-search endpoint checks active room types and
returns a hotel when at least one room type has inventory available for
the entire requested date range.

**Implementation item to verify before submission:** the hotel details
page should filter individual room categories using the selected dates.
If it still displays every active room category, record this as an
unfinished item or complete the filter.

### 5.4 Booking creation and cancellation

Booking creation runs in a transactional service method. It retrieves
the room type using the repository locking query, checks that it is
active, validates inventory, calculates the total, generates a booking
reference, and saves the booking with confirmed status.

Cancellation retrieves the booking by reference, verifies the guest
email, rejects an already-cancelled booking, and changes the status to
cancelled. Availability queries count only confirmed bookings, so
cancelled reservations no longer reduce available inventory.

## 6. Simultaneous bookings and concurrency

The booking service uses a database locking query when retrieving a room
type for booking creation (`findByIdForUpdate`). The intention is to
serialize competing booking attempts for the same room type and prevent
both requests from consuming the same remaining inventory.

The availability check and booking save are performed within a
transactional service method. The database lock must remain held until
the transaction completes.

For stronger verification, run an integration test that sends two
booking requests for the final available room at the same time and
confirms that no more than the configured inventory is confirmed. Review
lock mode, transaction boundaries, isolation level, and database
behaviour together. Do not claim this scenario is fully proven until
that test has passed.

## 7. Surprise feature -- Smart Stay Recommendation Engine

### Purpose

A traveller may know the destination and budget but be unsure which
property or room best fits the trip. The recommendation feature narrows
the available room options using preferences.

### Inputs

The recommendation flow considers destination, maximum budget, guest
count, trip purpose, traveller type, and stay preference.

### Implementation

The backend filters active room types and hotels using destination,
budget, and guest capacity. It then applies deterministic rule-based
scoring using the selected preferences and available room/hotel
attributes. Results include a recommendation score and a human-readable
reason.

This is a rule-based recommendation feature, not a trained
machine-learning model. It was chosen because the sample dataset does
not provide labelled data for training a model, and the rules are
lightweight and explainable.

## 8. Design decisions and trade-offs

### React and Spring Boot

React provides a component-based frontend. Spring Boot provides a
structured Java backend and REST API. Separating the two makes the
UI/API boundary and responsibilities clear.

### MySQL and relational entities

Hotel, room type, and booking data have clear relationships and
consistency requirements. MySQL supports relational constraints and
transactional operations.

### Backend-owned pricing

The frontend estimate improves usability, but the backend calculates the
final amount from stored room pricing to avoid trusting browser-supplied
prices.

### Rule-based recommendations

A rule-based approach is more suitable than machine learning for a small
sample dataset without labelled training data. It is also easier to
explain and adjust.

### Date-range overlap

An exclusive check-out date follows common hotel booking conventions and
permits a new stay to begin on the date another stay ends.
